# 原始数据缺失与异常处理方案

> 面向对象：产品经理 / 业务团队  
> 关联文档：pvas_external.md（标准评估方案）  
> 版本：v1.0 | 2026-05-28

---

## 一、缺失场景全景

### 1.1 设备侧缺失（数据根本没采集到）

| 场景 | 触发原因 | 缺失范围 |
|-----|---------|---------|
| 项圈没电关机 | 电量耗尽 | IMU + ENV 全部缺失 |
| 充电中取下 | 主人主动取下 | IMU + ENV 全部缺失（WEAR = NOT_WORN） |
| 固件崩溃重启 | Bug / 内存溢出 | 重启前后数据连续性断裂，有短暂空洞 |
| 本地存储写满 | 未及时同步且存储耗尽 | 最旧的一段被新数据覆盖，丢失不可恢复 |

### 1.2 传输侧缺失（采集到了但没上来）

| 场景 | 触发原因 | 影响 |
|-----|---------|-----|
| 蓝牙断连 | 手机不在旁边、超出范围 | 数据滞留设备，下次连接时延迟上传 |
| 服务端丢包 | 网络抖动 | 部分帧缺失，时间轴出现小段空洞 |
| 时钟漂移 | 设备时钟未对齐服务器时间 | 时间戳错乱，IMU 与 ENV 无法正确对齐 |
| 次日延迟同步 | 用户昨天未开 App | 昨日评分滞后，EWMA 基线需回填处理 |

### 1.3 数据质量问题（数据有但不可信）

| 场景 | 表现 | 受影响传感器 |
|-----|------|------------|
| 项圈松动 | WEAR = WORN_LOOSE，重力向量持续漂移 | IMU 全部、颈温 |
| 颈温传感器脱离皮肤 | neck_temp 与 env_temp 差值 < 1°C | 仅颈温 |
| IMU 量程溢出 | 加速度值超出 ±16g（如被摔落） | 仅加速度 |
| 传感器电气故障 | 某一路持续输出固定值或全 0 | 单传感器 |
| 时间戳重复 / 乱序 | 蓝牙重传导致重复帧 | 所有时序分析 |

### 1.4 局部时段缺失（最常见，碎片化）

不是全天缺，而是某几段空白：

| 典型案例 | 缺失时段 | 高风险影响 |
|---------|---------|---------|
| 白天充电 1 小时 | 日间连续 1h 空白 | S1/S2 低估（可能恰好是活跃抓挠时段） |
| 洗澡前取下 30 分钟 | 短暂空洞 | 影响较小 |
| 凌晨断连重连 | 夜间碎片空洞 | **S3 睡眠质量评估影响最大** |
| 出门旅游 2 天未充电 | 连续多天空白 | 基线更新、连续异常计数均受影响 |

## 二、核心处理规则

### 2.1 有效数据时长门槛

**当日有效 IMU 数据 ≥ 16 小时（2/3 天）才输出评分，否则标记为"数据不足"。**

| 有效时长 | 处理方式 | App 展示 |
|---------|---------|---------|
| ≥ 20 小时 | 正常评分，置信度不降 | 显示具体等级（如 L4） |
| 16–20 小时 | 评分有效，置信度降一档 | 显示等级 + "今日数据较少" |
| 8–16 小时 | 不输出评分 | "今日数据不足，建议保持佩戴" |
| < 8 小时 | 不输出评分，不更新基线 | "今日未采集到有效数据" |

> **不做时段外推**：不把已有数据乘以系数来补全缺失时段。原因：如果缺失的恰好是抓挠最集中的时段（如主人不在家那段），外推会系统性低估。宁可标注"数据不足"，也不给出误导性评分。

---

### 2.2 缺失时段的置信度标注

有效时长 16–20 小时时，系统记录缺失分布，影响置信度判断：

| 缺失分布 | 影响评估 | 置信度调整 |
|---------|---------|---------|
| 白天缺失（9:00–21:00） | S1/S2 可能低估 | 置信度 -1 档 |
| 夜间缺失（22:00–6:00） | S3 睡眠评分不可信 | S3 单独标为"不可用"，总分重标定（去掉 S3，其余等比放大） |
| 随机分布缺失 | 影响均匀，影响较小 | 置信度不变 |

---

### 2.3 EWMA 基线的更新规则

| 当日情况 | 基线更新规则 | 原因 |
|---------|-----------|------|
| 有效时长 ≥ 16h，Z 正常 | 正常更新（权重 10%） | 可信数据，正常学习 |
| 有效时长 ≥ 16h，Z 异常 | 按软冻结规则降权（3% 或 0%） | 异常期不污染基线 |
| 有效时长 < 16h | **跳过，不更新基线** | 数据不足，不应影响基线 |
| WORN_LOOSE 超过 4h | 降权更新（权重 3%） | 数据可信度低 |
| 旅游 / 住院等连续多天缺失 | 连续跳过，基线保持冻结 | 特殊时期不代表日常状态 |

---

### 2.4 连续异常天数的计数规则

连续 N 天 Z > 2 触发分级告警，数据缺失的天处理如下：

```
连续异常计数规则：

  数据充足且 Z > 2  → 计数 +1
  数据充足且 Z ≤ 2  → 计数重置为 0
  数据不足（跳过天）→ 计数保持不变，不重置，不累加

举例：
  Day1: Z=2.5 → 计数=1
  Day2: 充电缺数据 → 计数仍=1（跳过，不中断）
  Day3: Z=2.8 → 计数=2 → 触发"连续2天"轻提醒
  Day4: Z=0.5 → 计数重置=0
```

> **跳过而非中断的原因**：避免用户有意或无意通过充电"绕过"告警计数重置。数据不足不等于状态恢复正常。

---

### 2.5 WORN_LOOSE 的处理

| 持续时长 | IMU 数据处理 | 颈温处理 |
|---------|-----------|---------|
| < 30 分钟 | 正常使用，标注低置信度 | 正常使用 |
| 30 分钟–4 小时 | 降权处理（对 S1/S2 贡献降至 50%） | 该时段颈温标为无效 |
| > 4 小时 | 视为"有效但低质数据"，该时段不计入 S3 睡眠评估 | 全段无效 |
| 全天 WORN_LOOSE | 当日颈温不输出，S4 = 0，其余重标定 | 全天无效 |

---

### 2.6 延迟上传的回填处理

蓝牙断连后次日同步，或用户多天不开 App，数据最终会上传。

| 处理步骤 | 说明 |
|---------|------|
| 按实际采集时间打分 | 数据时间戳是 Day1，即使 Day2 才上传，仍按 Day1 计算 |
| 按日期顺序回填 EWMA | Day1 数据在 Day2 之前更新基线，保持时序一致性 |
| 历史评分可追溯修正 | 延迟上传后，历史某天评分可能从"数据不足"变为有效评分 |
| App 显示"补全标记" | 补全的历史日期在 App 上显示"数据已补全"标记，避免用户困惑 |

---

### 2.7 传感器电气故障的检测与降级

**故障检测规则（服务端实时检查）：**

| 故障特征 | 判定逻辑 | 处理 |
|---------|---------|------|
| 加速度某轴持续输出固定值 | 连续 5 分钟方差 < 0.001 | 标记该轴故障，报警工单 |
| 陀螺仪全 0 | 连续 10 分钟全为 0 | 同上 |
| 颈温长期等于环境温度 | neck_temp - env_temp < 0.5°C 超过 30 分钟 | 标记 WORN_LOOSE 或颈温传感器故障 |
| 时间戳乱序 | timestamp[n+1] < timestamp[n] | 去重 + 排序，记录异常帧数 |
| IMU 量程溢出 | abs(acc) > 15.5g | 该帧标记为 SATURATED，从行为识别中剔除 |

**降级策略：**

```
单轴故障：
  加速度 X 轴故障 → 用 Y、Z 轴重建合向量，精度略降
  陀螺仪 X 轴故障 → 降级为仅用加速度分类，准确率从 87% 降至约 72%

颈温传感器故障：
  S4 = 0，其余维度等比放大（满分从 100 → 90 → 归一化回 100）

IMU 全部故障：
  S1 = S2 = S3 = 0，当日评分无效，输出"传感器异常，建议联系客服"
```

## 三、各评分维度的缺失影响汇总

| 评分维度 | 正常满分 | 数据不足时 | 对应降级方案 |
|---------|---------|---------|------------|
| S1 抓挠频次（25分） | 25 | 有效时长 < 16h → 不计算 | 当日评分无效 |
| S2 抓挠强度与时长（25分） | 25 | 同上 | 同上 |
| S3 主睡眠质量（20分） | 20 | 夜间数据缺失 → S3 单独无效 | 去掉 S3，其余等比放大 |
| S4 颈部体温（10分） | 10 | 颈温传感器故障 / 全天松动 | S4 = 0，其余等比放大 |
| S5 问卷结果（15分） | 15 | 用户不互动 | 参见 pvas_passive_mode.md |
| S6 环境修正（±5分） | ±5 | ENV 传感器故障 | S6 = 0（中性，不加减分） |

## 四、评分有效性判定流程

```
每日评分计算前，执行以下检查：

Step 1：计算有效 IMU 时长
  有效时长 = 总时长 - NOT_WORN 时长 - 固件重启空洞时长
  有效时长 < 16h → 输出"数据不足"，终止评分

Step 2：检查传感器状态
  存在全轴故障 → 输出"传感器异常"，终止评分
  存在单轴故障 → 标记降级，继续评分

Step 3：检查 WORN_LOOSE 占比
  WORN_LOOSE > 4h → 颈温 S4 标为无效，等比放大其余维度

Step 4：检查夜间数据完整性
  22:00–06:00 有效数据 < 4h → S3 单独无效，等比放大其余维度

Step 5：正常计算 S1–S6，输出总分和等级
  附加置信度标注（高 / 中 / 低 / 不可用）
```

## 五、用户侧感知设计

| 情况 | App 展示 | 说明 |
|-----|---------|------|
| 数据充足，评分正常 | 显示等级 + 趋势 | 正常状态 |
| 有效时长 16–20h | 显示等级 + "今日数据较少" | 轻提示 |
| 有效时长 < 16h | "今日未完成监测，建议保持佩戴" | 不输出等级 |
| 夜间数据缺失 | "睡眠数据不完整，部分评估不可用" | 不输出 S3 |
| 传感器故障 | "传感器异常，请检查项圈，联系客服" | 工单触发 |
| 延迟补全数据 | 历史日期旁显示"已补全"小标签 | 不干扰当前日期 |
| 连续多天数据不足 | "旺旺已 X 天未完整佩戴，健康监测已暂停" | 超过 3 天触发 |

## 六、对 XGBoost 模型的影响

第二阶段引入 XGBoost 评分后，数据缺失转化为**特征缺失问题**：

| 缺失类型 | XGBoost 处理方式 |
|---------|---------------|
| 某日 IMU 有效时长 | 作为独立特征输入（0–24 小时），模型学习"数据量"本身的含义 |
| S4 颈温无效 | 用 -1 填充，模型区分"0 分正常"与"缺失" |
| WORN_LOOSE 时长 | 作为独立特征（每日松动小时数） |
| 历史缺失天数 | 近 7 天、近 30 天的有效天数比例作为特征 |

XGBoost 在训练时覆盖"完整数据"和"缺失数据"两类样本，使模型对缺失值具备鲁棒性，不需要在特征工程层面人工填补。

---

## 七、总结

| 缺失类型 | 核心处理原则 |
|---------|-----------|
| 有效时长 < 16h | 不评分，不更新基线 |
| 缺失时段分布影响评分 | 夜间缺失 → S3 单独无效；白天缺失 → 置信度降档 |
| WORN_LOOSE > 4h | 颈温无效，IMU 降权 |
| 延迟上传 | 按实际采集时间打分，EWMA 按日期顺序回填 |
| 连续异常计数遇缺数据 | 跳过（保持计数），不重置，不累加 |
| 传感器故障 | 单轴降级继续，全轴故障终止评分并推送工单 |

> **核心原则：宁可标"数据不足"也不输出低质量评分；缺失不等于正常，连续告警计数不因充电而中断。**
